## GPU compute — RADV / Vulkan (vkprobe2, this session)

FMA kernels mirrored exactly across stacks (same chain math, thread counts, K, copy size as the
OpenCL bench). FP32 base kernel = 2 chained vec4 FMA updates/iter (32 flop/thread/iter).

| Test | Result |
|---|---|
| FP32 WG64 | 2,805.7 / 2,858.8 / 2,859.3 GFLOPS |
| FP32 WG128 | 2,691.1 / 2,676.8 / 2,671.0 GFLOPS |
| FP32 WG256 | 2,849.8 / 2,851.3 / 2,825.8 GFLOPS |
| FP32 WG512 | 2,830.6 / 2,854.6 / 2,861.6 GFLOPS |
| FP64 base | 113.4 / 113.2 / 113.5 GFLOPS |
| FP64 ILP2 | 113.3 / 113.3 / 113.7 GFLOPS (no change — FP64 is rate-bound) |
| Copy bandwidth | **129.8 GB/s** (best of 5, 0.54 GB moved) |

**FP32 sustained ≈ 2,858 GFLOPS** at WG64/256/512 (WG128 is a consistent ~6% valley).
That is **3.2× the Clover/OpenCL result on the same silicon, same math** (896 GFLOPS, below).
INFERENCE: 2,858 GFLOPS = 1,152 lanes × 2 flop × ~1.24 GHz — the 800 MHz console-OS clock in the
first report was the console operating point, not this kernel's. The first report's "spec peak
1,843 GFLOPS" framing is superseded by measurement (see jupi-vulkan/RESULTS-20261107.md erratum).

## The wide-chain anomaly (measured, unexplained, NOT claimed as throughput)

Four independent FMA chains per iteration (64 flop/thread/iter) measure **~7,050–7,160 GFLOPS
apparent** — 2.45× the 2-chain kernel, above the ceiling the 2-chain kernel implies. This number
is **not** published as achieved FMA throughput. What was run against it:

- SPIR-V verified complete on-box (spirv-dis: 8 OpFMul / 15 OpFAdd in the ILP module — glslang
  eliminated nothing).
- K-scaling is linear (K500 → 0.0015 s, K2000 → 0.0054 s, K8000 → 0.0211 s) — the loop runs.
- Output readback verified: out[0] = +inf (bits 0x7f800000), the mathematically correct saturated
  result — the math executed.
- Controls all reproduce ~7,000: per-thread seeded chains (no constant folding possible),
  fully distinct vec4 components (no splat symmetry), 8 chains at half K (same total, same time).
- Same harness, same session: the 2-chain control holds 2,865 GFLOPS — the harness is exonerated.
- FP64 shows no such effect (113 either way).

Standing interpretation: a RADV/ACO backend compilation effect on wide independent-chain compute
loops, mechanism unidentified. Filed open. Reproduction = fma32_ilp*.comp in this directory.

## CPU (numpy / OpenBLAS 3.12.0, 2048×2048 GEMM, best of 3)

| Threads | SGEMM | DGEMM |
|---|---|---|
| 1 | 0.7 GFLOPS (23.742 s) | 0.6 GFLOPS (26.453 s) |
| 2 | 0.7 GFLOPS (23.926 s) | 0.6 GFLOPS (26.805 s) |
| 4 | 0.7 GFLOPS (23.621 s) | 0.6 GFLOPS (26.580 s) |
| 8 | 0.7 GFLOPS (23.884 s) | 0.6 GFLOPS (26.774 s) |

**The thread count changes nothing** — and the absolute level is the story. This morning's
platform survey recorded 26.6 / 11.6 GFLOPS for scoped batch GEMM (1024³) on this same unit, and
the same 0.7 / 0.6 for unscoped runs — a ~19–38× regime gap that reproduces exactly here.
The suite's shell affinity is unrestricted (Cpus_allowed_list 0-7, verified in-process), so this
is not cpuset confinement. numpy reports its BLAS as OpenBLAS 3.12.0 via pkg-config with
configuration "unknown". HYPOTHESIS: the system numpy's BLAS path is a generic/reference-grade
kernel set that neither vectorizes for Jaguar nor honors the thread count, while the platform's
scoped job path runs a properly built stack.

**Supplement (cpu-supplement.txt): the placement falsifiers.** A taskset sweep re-ran the same
2048³ GEMM pinned to core 0 (1 thread), cores 0,2 (2), cores 0–3 (4), and cores 0–7 (8):
**0.7 / 0.7 GFLOPS in every cell** (best times 23.600–23.920 s / 26.061–26.390 s) — identical to
the unpinned sweep. A 1024³ comparability point (the survey's own size, default threads) also
lands at 0.7 / 0.6. So the collapse is **not** thread count, **not** shell affinity (verified
0–7 in both shells), **not** core placement, **not** matrix size. Everything a process can vary
from outside has been varied; the regime travels with the distro numpy/BLAS build itself. The
one test left standing — the one that would settle it — is the same GEMM inside the platform's
own Python environment, whose scoped jobs produced the survey's 26.6 / 11.6: if it flies there,
the pinned configuration simply specifies that environment, and the distro stack is marked
do-not-use for compute. That test needs the platform seat's lane and is filed as the open
follow-up, not silently assumed.

CPU misc (single process, default placement): **MEMCOPY 8.0 GB/s** (best 0.067 s, 0.54 GB moved);
**SHA256 (hashlib, one thread) 87.3 MB/s** (512 MiB in 5.866 s, digest 9acca8e8c222…).

## Crypto (openssl speed, -elapsed, 3 s per size)

The suite's combined invocation (`openssl speed -elapsed -seconds 3 sha256 aes-256-gcm`) aborted
on this build: `speed: Unknown algorithm aes-256-gcm` — no crypto numbers from the suite pass.
Repaired with a top-up that runs each algorithm separately and probes what this openssl accepts
(crypto-topup.txt in the raw outputs). The build is OpenSSL 3.6.5; AES-256-GCM **is** present in
its cipher list (id-aes256-GCM) — the speed app just requires the `-evp` form for it here.

| Algorithm | 16 B | 256 B | 1024 B | 16384 B |
|---|---|---|---|---|
| SHA256 | 11.2 MB/s | 60.5 MB/s | 81.0 MB/s | **90.6 MB/s** |
| AES-256-GCM (-evp) | 15.8 MB/s | 181.7 MB/s | 427.8 MB/s | **777.6 MB/s** |
| AES-256-CBC | — | — | — | **351.0 MB/s** |

The dedicated instruction paths are healthy: AES-GCM at ~778 MB/s is AES-NI working as it should,
and SHA256's 90.6 MB/s agrees with the hashlib figure above (87.3 MB/s). Contrast with the GEMM
and inference results below — the collapse is in generic compute paths, not in the silicon.

## Storage (fio, internal drive image, direct I/O)

| Test | Result |
|---|---|
| Sequential write, 1 GiB, 1M blocks, libaio iodepth 8 | **15.4 MB/s** (69.8 s) |
| Sequential read, 1 GiB, 1M blocks, libaio iodepth 8 | **67.9 MB/s** (15.8 s) |
| Random read, 4k, 256 MiB | 34.9k IOPS / 143 MB/s — **cache-resident, not a device figure** (the file had just been laid out by fio and sat in page cache; IOPS spread min 8.8k / max 43.0k over 3 samples) |

The honest device story is the first two rows: the root stack — an ext4 image file (loop0) on a
UFS partition, on a 5400 rpm HGST, behind Sony's USB-SATA bridge — writes at ~15 MB/s and reads
at ~68 MB/s. Write-heavy workloads do not belong on this root; the platform's design (checkpoints
and bundles on HCDU, working data staged deliberately) already assumes exactly that. Note the
read/write tests' files were laid out by fio immediately before measuring (fio default behavior).

## Inference (ollama, qwen3:0.6b Q4_K_M, server-side eval counters)

Five fixed prompts, seed 42, temperature 0, num_predict 128. Server-side counters only
(eval_count / eval_duration from the ollama API — not client wall-clock):

| Run | Generation | Prompt eval |
|---|---|---|
| 1 | 0.44 tok/s (128 tok in 288.96 s) | 10.5 tok/s (27 tok) |
| 2 | 0.44 tok/s (128 tok in 288.48 s) | 8.1 tok/s (21 tok) |
| 3 | 0.44 tok/s (128 tok in 288.42 s) | 8.0 tok/s (23 tok) |
| 4 | 0.44 tok/s (128 tok in 288.91 s) | 7.1 tok/s (17 tok) |
| 5 | 0.44 tok/s (128 tok in 289.01 s) | 12.8 tok/s (35 tok) |

**Median generation: 0.44 tok/s** — and the five runs agree to within 0.6 s of each other. That
uniformity is itself the signal: this is a hard regime limit, not noise. During the section the
llama-server process held ~6.8 cores busy for the full 24 minutes (≈2.8 CPU-hours), i.e. the
threads burn continuously while tokens emerge at 0.44/s — the signature of the same collapsed
default path the GEMM sweep hit, not of a model or hardware limit (the same silicon sustains
2,858 GFLOPS FP32 through RADV and 778 MB/s AES-GCM through AES-NI in the same hour). Read
together with the CPU section: JUPI's naive/default software paths (distro numpy BLAS, stock
ollama placement) collapse by one to two orders of magnitude, while its tuned paths perform.
Pinning the configuration means pinning the paths, not just the hardware — which is precisely
what the platform profile work is for. The mechanism of the collapse is HYPOTHESIS at this
writing (thread-pool spin plus unvectorized kernels is the leading candidate); the numbers are
measured fact, five times over.

## Method notes

- Every source file was hash-gated onto the box (sha256 on-box == desk) before compiling.
- vkprobe2.c was assembled on-box from the already-verified vkprobe.c head (16,019 B, byte-identical)
  plus a 3,680 B new tail — the gadget's staged-write cursor dropped 9 bytes on a hand-carried chunk,
  so the file was rebuilt from verified slices instead of re-carried. Final on-box sha256:
  165397a9ce5ecf2f220a5d92e76a2b7977d1b4b406c14c3dfeb78e39f88c26dc.
- Thermal trace (2 s samples, hwmon1) ships with the raw results.
- Collection: the suite outputs were tarred on-box and ferried as one archive (122,880 B,
  sha256 6ecc00f7… verified after reassembly) — every member file then verified against the
  on-box SHA256SUMS list, 12/12 OK. Two earlier desk-side copies made by hand-carrying base64
  were corrupted in transcription and caught by the same gates (size + sha256) before use;
  they were deleted and replaced by the archive path. Nothing unverified is quoted anywhere
  in this report.
- The two top-up scripts' first launch failed on a missing execute bit (landed files are
  mode 0600); relaunched via explicit `bash <script>`. The relaunch invoke itself reported a
  timeout — the known gadget artifact when a command backgrounds a detached tree; state was
  verified on-box before proceeding, and no duplicate run occurred.
- Sanity-read artifact: the suite's FP32 sanity read after the FP64 test reads 0.0 — the buffer's
  last writer was the FP64 kernel; the first 4 bytes of a double +inf read as float are 0.0.
  The dedicated readback in vkprobe3 confirms +inf (0x7f800000) for the FP32 kernels.
